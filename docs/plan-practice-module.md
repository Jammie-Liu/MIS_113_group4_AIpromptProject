# 練習題 + 系統功能（負責人：hsuyunling33）討論與實作計畫

此檔案是「練習題＋其他系統功能」這塊後端工作的討論大綱與實作 to-do list，
給負責人自己跟進進度，也給組員／各自的 AI 助理了解這塊的範圍與現況。
更新方式跟 [CHANGELOG.md](CHANGELOG.md) 一樣：不要整份重寫，勾選/補充即可，
大改動時另外在 CHANGELOG.md 記一筆。

**範圍界定**：這塊對應原型裡的「教學面」——[學生端原型](../frontend/src/prototypes/學生端_最初版.html)
的首頁地圖／題庫／關卡練習(dojo)／競賽紀錄／個人資料／設定；不含「競賽」（arena、教師監控台），
那是另一位後端負責的部分，兩邊會共用「題庫、提交、評分」這幾個核心模組，見下方討論項目。

---

## Part 1：討論大綱（開工前要跟團隊對齊的事）

跟另一位後端 / 管理者 / 前端討論，把下面問題定案，再開始寫程式，避免寫到一半要重改。

- [ ] **1-1｜共用模組怎麼分**：題庫、提交（submission）、評分（scoring）這三個模組，
      練習題跟競賽是否共用同一套？如果共用，誰主責維護（你 or 競賽那位）？
      （這是專案目前明確標記「還沒定案」的項目，優先討論）
- [ ] **1-2｜題庫怎麼擴充**：練習題題庫由「開發者」寫入——是寫死在程式碼/種子資料，
      還是要做一個簡單的後台介面讓開發者新增題目？(教師端原型裡已經有「新增題庫」的
      UI 設計可以參考，但那個是給教師建競賽案例用的，練習題是否比照辦理？)
- [ ] **1-3｜雙 AI 模型怎麼接**：
      - 用哪家/哪個模型 API（Anthropic Claude？OpenAI？）
      - 「產生回應」跟「4D 評分」是兩次獨立呼叫，還是一次呼叫要求模型回傳兩種結果？
      - 4D 評分的 prompt/rubric 怎麼設計、要不要先手動測幾個案例校準
      - 呼叫外部 AI 有成本與延遲，練習題（開放給任何學生無限次用）要不要做限流／快取
- [ ] **1-4｜登入／角色／權限系統歸誰做**：團隊已經定調這個要最先完成，因為競賽依賴它。
      需要跟另一位後端、管理者一起討論：這個算「練習題+系統功能」還是獨立的第三塊？
      由誰主責、預計何時完成（會卡住你跟競賽那位的後續開發）。
- [ ] **1-5｜API 規格**：跟前端 2 人對齊練習題相關的 API（見 Part 2 的端點草案），
      確認命名、資料格式、錯誤處理方式，形成文件後再各自平行開發。
- [ ] **1-6｜技術棧**：`backend/index.js` 目前是空的，需要團隊/你們兩位後端共同決定：
      Node.js 用什麼框架（Express／Fastify／Nest 等）、資料庫（PostgreSQL／MongoDB 等）、
      ORM 要不要用。建議跟另一位後端統一，避免兩塊模組用不同技術棧難以共用程式碼。
- [ ] **1-7｜資料表設計**：對照 [architecture.md](architecture.md) 列的 Models
      （User, Course, Case, Prompt, SubQuestion, Score, Comment），確認「練習題」需要的
      欄位跟「競賽」需要的欄位有哪些重疊、哪些不同，避免兩邊各自建表最後對不起來。
- [ ] **1-8｜建立 `CLAUDE.md`（repo 根目錄）**：團隊工作流程裡已經講好要放這個檔案，
      跟全組（跟大家各自的 AI）討論要放哪些規則，草案分類如下，開會時逐條確認要留/改/刪：
      - **每次開工前必做**：讀 `docs/CHANGELOG.md` 最新紀錄；讀自己負責模組對應的
        `docs/plan-*.md`；讀 `docs/architecture.md` 確認規劃沒過時
      - **每次改動後必做**：在 `docs/CHANGELOG.md` 最上面新增一則紀錄（不覆蓋舊的）；
        動到共用模組（題庫/提交/評分）要額外知會共同負責人
      - **Git 規則**：`main` 受保護、不直接 push、PR 要小而單一、需一人 review；
        討論/規劃文件放專屬 `discuss/*` branch 不進 main，只有實作完成的程式碼才進 main
        （這條目前只是使用者個人習慣，需要討論是否訂為全隊規則）；機密資訊一律用 `.env` 不 commit
      - **技術棧與資料夾結構**：隨專案進展持續更新（frontend 已定案 Vite+React，
        backend 待 1-6 討論定案後補上）
      - **命名規則**：目前完全沒定，需要討論（例如元件檔 PascalCase、資料夾/一般檔案
        kebab-case、API 路徑、資料庫欄位命名風格）
      - **AI 協作規則**：AI 可輔助寫程式碼/review，但最終要人工審核；每個人要能解釋
        自己那塊程式碼（口試準備）；機密資訊不貼給 AI
- [ ] **1-9｜Git 協作、減少人工 merge 衝突**：2026-09-23 pull main 時實際發生過「組員已經
      直接 push 東西到 main」的狀況，順便討論要不要採用以下做法：
      - 分支不要等到最後才對 main，開工前先 `git fetch` + `rebase origin/main`，
        小步同步、避免累積成一次難解的大衝突
      - 共用模組（題庫/提交/評分）在 Issue/看板認領任務時，順便標註「會動到哪些檔案」，
        避免兩位後端同時改同一支檔案的同一段
      - 要不要全隊統一 `git config --global pull.rebase true`，讓 pull 預設用 rebase、
        歷史更乾淨、衝突更好定位
      - 呼應 CLAUDE.md 已經定案的「push 到 main 前先 pull」，這幾條算是更進一步的補充建議，
        還沒定案，需要跟組員（尤其另一位後端）討論後才决定要不要收進 CLAUDE.md

## Part 2：實作 to-do list（Part 1 決策定案後依序進行）

### 里程碑 A：專案骨架與登入權限（阻塞後面所有工作）
- [ ] 依 1-6 的決定，初始化 `backend/` 專案（框架、資料庫連線、環境變數 `.env` 範本）
- [ ] 實作使用者資料表與登入/註冊 API（學生／教師／開發者三種角色，或依 1-4 討論結果調整）
- [ ] 實作角色權限中介層（Middleware）：例如只有「開發者」角色能寫入練習題題庫

### 里程碑 B：練習題題庫模組
- [ ] 依 1-2 的決定，設計題庫資料表（難度、題目內容、trap 陷阱說明、prefill 預填文字、
      checklist 檢查項目——可參考 [學生端原型裡 TASKS 物件](../frontend/src/prototypes/學生端_最初版.html)
      的現有欄位結構，那是前端目前寫死的假資料格式）
- [ ] 題庫 CRUD API（新增／查詢／(視 1-2 決定)編輯）
- [ ] 題庫列表 API（給學生端「解方發想題庫」畫面用，含難度篩選）

### 里程碑 C：提交與雙模型評分流程（核心機制）
- [ ] 依 1-3 決定的 AI 模型與呼叫方式，實作「送出提示」API：
      接收使用者 prompt → 平行呼叫「產生回應」模型 + 「4D 評分」模型 → 整合回傳
- [ ] 4D 評分模型的 prompt 設計與測試（D1 委託／D2 描述／D3 辨識／D4 審慎），
      確保回傳格式穩定可解析（例如要求模型輸出結構化 JSON）
- [ ] 每次提交次數限制邏輯（原型是每關最多 3 次，含攻擊/濫用防範，例如同一使用者短時間
      大量呼叫要不要做限流）
- [ ] 提交紀錄與分數儲存（供之後「競賽紀錄」「個人資料」頁面查詢歷史）

### 里程碑 D：其他系統功能
- [ ] 個人資料 API（4D 能力總覽、教學面練習紀錄——對照
      [學生端原型 PROFILE 畫面](../frontend/src/prototypes/學生端_最初版.html)）
- [ ] 練習紀錄／歷史查詢 API（對照原型 HISTORY 畫面）
- [ ] 設定相關 API（顯示名稱、通知開關、隱私設定——注意目前原型「深色模式」開關是純前端
      UI 狀態，不一定需要後端儲存，其餘設定項目才需要）
- [ ] 登出功能（原型目前按鈕沒接，屬於這塊）

### 里程碑 E：整合與文件
- [ ] 補齊 API 文件（給前端對接用，呼應 1-5）
- [ ] 針對評分邏輯、提交流程寫基本測試（單元測試 + 一條完整流程的整合測試）
- [ ] 完成一個里程碑就在 [CHANGELOG.md](CHANGELOG.md) 補一則紀錄
