# AI 角色總覽

這份文件說明系統裡所有的 AI：有哪些角色、各自做什麼、練習和競賽為什麼要分成不同角色。
後端實作 AI 相關功能前，請先讀這份。

- 負責人：亭慧（AI 邏輯負責人）

- 購買、模型與費用：[ai-api-setup.md](ai-api-setup.md)
- 系統流程：[system-flow.md](system-flow.md)

## 一、總表：3 種引擎 × 6 個角色

所有 AI 都使用 **Anthropic（Claude）**，共用同一個 API 帳號。

- **引擎**：後端的一個模組，負責用某一種固定方式呼叫 Claude API（輸入什麼、輸出什麼格式、什麼時候呼叫）。
- **角色**：同一個引擎在練習和競賽各有一種用法，差別在 system prompt、輸入資料、輸出欄位與呼叫時機。
  **不是訓練或修改模型**，模型本身完全相同。

| 引擎 | 練習的角色 | 競賽的角色 | 輸出 | 呼叫方式 |
|---|---|---|---|---|
| 回答 | 練習回答 AI | 競賽回答 AI | 一般文字回覆 | 串流 |
| 評分 | 練習評分 AI | 競賽評分 AI | 固定格式 JSON（0／1／2、證據、理由…） | 結構化輸出，回合結束時評一次 |
| 偵測 | 練習 4D 行為偵測 AI | 競賽面向偵測 AI | 固定格式 JSON（出現了哪些項目） | 結構化輸出，背景執行，只送新增的內容 |

**大原則：練習是「教學」，競賽是「測量＋排名」。** 下面大部分的差異，都是從這個目的不同推出來的。

---

## 二、回答引擎

**共同點**：中立的一般助手；都**不知道題目背景**，要靠學生自己交代（這是在測「描述」能力）；串流回覆；不參與評分。

| | 練習回答 AI | 競賽回答 AI |
|---|---|---|
| 對話單位 | 一位學生、一題、一個回合 | 一位學生、一場競賽的一個回合 |
| 對話記憶 | 回合內保留，離開再回來可以接續 | 回合內保留，每回合開始時清空 |
| 誰看得到對話 | 只有自己 | 同組組員互相看得到；老師看得到每位成員 |
| 使用壓力 | 沒有時間限制 | 有倒數，全班在同一段時間大量送出 |

**為什麼分成兩個角色**：回答的行為幾乎一樣，system prompt 可以共用。分開主要是因為：
- 對話存放的位置不同：練習存在「某題的某回合」，競賽存在「某場競賽、某隊、某回合」，評分時要能找回正確的對話。
- 競賽時全班同時使用，流量集中，後端可能要另外處理排隊或限速。
- 保留之後各自調整的彈性，互不影響。

## 三、評分引擎

**共同點**：使用同一套 **4D 判斷卡**與通用判斷規則；AI 只判斷 0／1／2 並附證據與理由，分數由後端程式計算；在**回合結束時**評分，不即時評；使用結構化輸出。

| | 練習評分 AI | 競賽評分 AI |
|---|---|---|
| 目的 | 給學生回饋，幫助學習 | 測量能力、排名 |
| 評分單位 | 個人 | 4D 以個人為單位；解方以組為單位 |
| 評哪些 4D 指標 | 只評**該題的適用指標** | **全部**核心＋進階指標 |
| 評什麼成果 | 學生**提交的成果** | 組內**投票選出的最終回答**（某位組員的個人結果） |
| 解方評分 | 只有困難題，**只當回饋** | 每回合都有，**計入排名** |
| 額外產出 | **完成檢查**（交付規格逐條判斷） | **完整集體知識地圖**的資料（不另外呼叫） |
| 「未觀察到」 | 有（例如按「要提示」提早結束） | 無 |
| 「不確定」誰處理 | 沒有老師，照樣計入熟練度 | 列給老師評分時參考 |
| 呼叫時機 | 提交或要提示時 | 每回合投票完成後 |
| 計入個人 4D 能力 | 只有**回合 1** | **每一回合** |

**為什麼分成兩個角色**：
1. **評分範圍不同**：練習一題只練一兩個行為，評全部指標會讓沒練到的都變 0 分；競賽要比較全班，就要評完整的 4D。
2. **評分對象不同**：練習是個人作答、個人提交；競賽同時要產出個人分數（4D）和組分數（解方）。
3. **結果用途不同**：練習用來回饋與解鎖（完成檢查）；競賽用來排名與畫知識地圖。
4. **有沒有人覆核不同**：競賽有老師看標記，練習沒有，所以「不確定」的處理方式不同。

**判斷卡必須共用**：同一個行為在練習和競賽要用同一把尺評分，合併成個人 4D 能力報表時才公平。

## 四、偵測引擎

**共同點**：輕量、背景執行、**只送新增的內容**；**只判斷「有沒有出現」，不打分、不計入任何分數**；畫面標示「即時，不是正式評分」；使用結構化輸出。

| | 練習 4D 行為偵測 AI | 競賽面向偵測 AI |
|---|---|---|
| 偵測什麼 | 學生的 **4D 行為**（例如「查證事實」） | 解方涉及的**面向**（例如「業者生計」） |
| 依據的清單 | 4D 行為清單 | 該題答案參考庫的面向清單 |
| 單位與頻率 | 每位學生，**每送出一則** | 每一隊，**每 1～2 分鐘批次一次** |
| 什麼時候開始 | **回合 2 以後**（回合 1 不做） | 競賽一開始就做 |
| 誰看得到 | 只有學生自己 | **全班學生與老師**（集體知識地圖，指導教授最初的設計） |
| 額外工作 | 判斷成果是否已達交付規格，顯示「可以提交了」 | 整理每個面向的代表摘要；歸併相近的新面向 |
| 結果用在哪 | 即時行為標籤、側邊「本回合觀察到的行為」、結果面板「本回合還展現了」 | 即時集體知識地圖、各隊覆蓋率（覆蓋率由程式計算） |

**為什麼分成兩個角色**：
1. **偵測的對象不同**：練習看「學生怎麼用 AI」（4D 行為），競賽看「解方涵蓋了什麼」（面向）。清單、判斷方式、輸出欄位都不一樣。
2. **頻率不同**：練習是個人學習，每則回饋最有幫助；競賽是全班同時進行，每則偵測太貴，所以改成每隊批次。
3. **開始時機不同**：練習的回合 1 是診斷、熟練度取自回合 1，即時標籤等於變相提示；競賽沒有這個問題。
4. **公開範圍不同**：練習的結果是個人的；競賽的知識地圖是全班共享，摘要要寫成適合公開的內容。

## 五、總整理

| 引擎 | 共用的部分 | 分開的主要原因 |
|---|---|---|
| 回答 | 行為、system prompt 幾乎相同 | 資料歸屬與流量不同，保留各自調整的彈性 |
| 評分 | 4D 判斷卡、0／1／2 規則 | 評分範圍、評分對象、結果用途、有沒有老師覆核都不同 |
| 偵測 | 輕量、增量、不計分的做法 | 偵測對象（行為 vs 面向）、頻率、開始時機、公開範圍都不同 |

## 六、對應的後端模組

見 [architecture.md](architecture.md) 的 Services：

| 模組 | 對應引擎 | 說明 |
|---|---|---|
| `answerService` | 回答 | 練習與競賽的回答 AI |
| `scoringService` | 評分 | 練習與競賽的評分 AI；幻覺判斷、完整集體知識地圖資料也在這裡產出 |
| `detectionService` | 偵測 | 練習的 4D 行為偵測（含建議提交）、競賽的面向偵測 |
| `knowledgeMapService` | （不呼叫 AI） | 整理集體知識地圖：即時版用偵測結果、完整版用評分結果；計算覆蓋率 |
